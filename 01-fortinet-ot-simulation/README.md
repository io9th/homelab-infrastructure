# OT Security Lab: Logical Provisioning of FortiOS (FortiGate) on Proxmox
## Context and Prediction

Managing networks in Operational Technology (OT) environments, such as electrical power utilities, requires specific hardware. Unlike conventional IT, substations deal with dust, vibration, and extreme temperature spikes. That is why equipment like the **FortiGate Rugged 60F (NGFW)** and the **FortiSwitch Rugged 424F-POE** are *fanless* and built in heavy-duty metal to withstand up to 60°C and electromagnetic interference (EMI).

The objective of this lab is to simulate the logical provisioning of an OT-focused Fortinet environment using a virtual machine (KVM) on Proxmox. The initial prediction is to establish an isolated topology (OT LAN vs. WAN), provision secure remote access, and configure packet routing with inspection.

# 1. Image Deployment and Hypervisor Configuration

The image used was the KVM version (New Deploy FortiGate) provided by Fortinet. The transfer to the host was done via SFTP, and the disk was imported via CLI:

```bash
qm importdisk [VM_ID] /path/fortios.qcow2 local-lvm
```

VM Hardware Parameters: 1 Socket, 1 Core, 2048MB RAM, Network vmbr0 (VirtIO).

**Error Observation:** Kernel Panic on Boot
On the first boot, the system hung indefinitely on the *"Formatting shared data partition"* process.

**Explanation:** FortiOS has strict cryptography and hardware validation requirements that do not operate well with generic CPU masks.
**Resolution:** Changed the processor type in the Proxmox UI from kvm64 to host. This exposes the actual CPU flags (Intel/AMD) to the VM, allowing the system to successfully format the disk.

# 2. Remote Access and Subnet Routing via Tailscale

To avoid directly exposing the firewall on the local network, access to the management interface (Port 1) was established by configuring the Proxmox host as a subnet router on Tailscale.

```bash
# Identifying the DHCP IP of the firewall via the VM console
get system interface physical

# On the Proxmox host: advertising the subnet
tailscale up --advertise-routes=192.168.100.0/24 --accept-routes
```
Troubleshooting Note: If the route does not propagate correctly, it is necessary to force IPv4 packet forwarding in the Linux host kernel:

```bash
echo 'net.ipv4.ip_forward = 1' | sudo tee -a /etc/sysctl.d/99-tailscale.conf && sudo sysctl -p /etc/sysctl.d/99-tailscale.conf
```

# 3. Logical Segmentation (LAN vs. WAN)

The traffic from Programmable Logic Controllers (PLCs) and sensors must be isolated from the outbound internet network. Port 2 was configured as the internal network Gateway (OT LAN).

**Addressing Mode:** Manual (Static IP). Critical infrastructure devices act as network references and cannot rely on dynamic IPs.

**DHCP Server:** Enabled for the subnet.

**Lease Time:** Set to 7 days.

- Note: The lease time for a guest network (like an airport) is usually 1 hour due to high device turnover. In isolated industrial or corporate networks, devices are highly static. A longer lease time (7 days) is much more efficient as it reduces IP renewal broadcast traffic on the network.

# 4. Rule Abstraction: Objects and Policies

## The Concept of Objects

Managing raw IPs in firewall rules makes maintenance unsustainable. In FortiOS, we use Objects (Address, Service, and User).
In programming terms, a network Object works exactly like the #define directive in C. Instead of hardcoding the server IP across dozens of rules, we create an alias:

```C
#define scada_server = "10.10.10.50"
#define telemetry_port = "Port 8080"
```

If the server IP changes, we only modify the central object, and all policies inherit the update automatically. I configured objects of type Subnet (for entire departments) and FQDN (Fully Qualified Domain Name, for external APIs).

## Firewall Policies 

Packet flow through a firewall can be understood as a sequential if/else structure, where the default case (else) is always an Implicit Deny.

An outbound policy (LAN -> WAN) was created with the following parameters:

**Source:** LAN_OT Object

**Destination:** ALL

**Services:** HTTP, HTTPS, DNS, ALL_ICMP (Restricted specifically to outbound traffic, allowing ping tests without exposing the internal network to external scanning).

**NAT:** Enabled. The private LAN IP is masked (Network Address Translation) by the WAN interface IP to enable external routing.

# 5. Visibility and CLI Syntax (FortiOS)

The graphical user interface (GUI) readily displays Forward Traffic, but local traffic processed by the firewall itself is usually hidden by default to save disk I/O.
To enable the visualization of packets generated by the firewall itself (such as ping tests initiated from the device), we must use the CLI.

The FortiOS CLI features a tree-like structure, similar to navigating directories in a file system.

```Plaintext
config log memory filter
    set local-traffic enable
end
```

Understanding the syntax:

`config:` Enters the configuration "directory".

`edit:` Selects a specific interface or item.

`next:` Saves the current configuration and returns to the previous level of the tree (equivalent to closing a code block scope).

`end:` Saves all changes and exits the configuration tree entirely.

With this adjustment, it was possible to audit the entire lifecycle of the packets in the local traffic log, successfully validating the correct routing and the dropping of unwanted connections.
